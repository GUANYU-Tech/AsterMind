Making Protocol Effects Explicit: LLM-to-Packet
Simulation for Superpod Interconnect Exploration
HPCA 2027 Submission#356
Confidential Draft
Do NOT Distribute!!
Abstract—Large language models (LLMs) have become the
foundation of modern AI services. The rapid growth of LLM
sizes and context lengths has exceeded the memory capacity
of a single GPU or NPU, requiring model partitioning across
devices. However, partitioning models across devices introduces
costly communication overhead, driving the need for superpods
with large-scale, high-bandwidth, low-latency scale-up fabrics.
Exploring superpod designs requires accurate interconnect sim-
ulation, as communication latency is jointly determined by
link technologies, topologies, and scale-up protocol-stack choices.
Latency-bandwidth models estimate communication latency us-
ing a startup term and a transfer term derived from message
size and effective bandwidth. But they fail to capture contention
and protocol effects, resulting in errors of up to 40%. Packet-
level simulators like ns-3 model routing, queueing, and packet
timing, but require protocol-specific LLM-to-packet implementa-
tions. The high simulation time also hinders efficient end-to-end
superpod evaluation and design exploration.
This paper presentsProtoBridge, an ns-3-based LLM-to-packet
simulator for superpod interconnect exploration. To make proto-
col effects explicit,ProtoBridgeintroduces two abstraction layers
over ns-3 to evaluate different scale-up protocols using a common
simulation substrate: (1) an operation-to-packet (OTP) layer that
captures protocol-specific packet exchanges and dependencies,
and (2) a packet-execution (PEX) layer that applies shared
packet-level mechanisms to the ns-3 event system.ProtoBridge
achieves average latency error of 17.8% on H200 NVLink4 and
10.3% on C500 MetaXLink. To enable faster superpod evaluation
for further interconnect exploration, we derive a surrogate model
that combines OTP parameters with analytical models of PEX
mechanisms. The surrogate reduces the mean absolute percentage
error (MAPE) from 55.7% of latency-bandwidth models to
11.8%, and reduces evaluation time from 2.38∼75.70 s to 20.5µs
per operation. Using the surrogate-to-simulator evaluation work-
flow, we explore 38,232 superpod designs across topologies, link
technologies, and protocol configurations in one hour. We use
ProtoBridgeto analyze two emerging superpod designs, scale-
up memory pool and co-packaged optics (CPO) interconnects,
revealing design insights for future LLM superpod architectures.

simulation would require hours or days to evaluate one serving

To make the protocol effects explicit and efficiently com-

abstraction layers, separating protocol-specific behavior from

a common simulation substrate, only requiring the users to
change the input configurations rather than reimplementing
protocol-specific packet behaviors.

interconnect exploration, we derive a protocol-defined latency

startup latency and effective bandwidth of the communication
operation. It also uses theoretical latency equations from PEX
mechanisms to model the effect on communication latency.
Therefore, the surrogate can accurately capture protocol effects
while reducing the modeling cost to several equations.

II. BACKGROUND
A. LLM Inference Communication
When model weights, KV cache, and activations exceed
the memory of one GPU or NPU, serving must partition
them across devices. Tensor parallelism combines partial layer
results with collectives such as AllReduce, ReduceScatter, and
AllGather [1]. Context parallelism exchanges attention data
across token partitions [11]. Expert parallelism uses AllToAll
for token dispatch and combination [3], while pipeline stages
exchange activations through point-to-point transfers [2]. KV
cache migration and prefill/decode disaggregation move KV
data between serving workers [12], [6], [5]. A scale-up-
attached memory pool additionally introduces remote-memory
reads and writes. These communications often gate subsequent
computation, placing their latency on the serving critical path.

Communication operations reach the fabric through differ-
ent logical exchange patterns. A collective algorithm decom-
poses a collective into transfers among the participating de-
vices. For AllReduce, ring, tree, or NVLink SHARP (NVLS)
determines the communicating peers, step order, and bytes sent
per step [13], [14], [15]. Point-to-point and remote-memory
operations instead use direct transfers or request-response
exchanges. The selected scale-up protocol configuration de-
termines how each exchange is packetized, controlled, and
completed. Together with fabric timing, the resulting packet
traffic and completion condition determine operation latency.
B. Superpods and Scale-Up Protocols
A superpod is a large group of GPUs or NPUs connected
by a high-bandwidth, low-latency scale-up fabric. Published
systems include NVIDIA GB200 NVL72 with 72 GPUs,
Huawei CloudMatrix 384 with 384 NPUs, and Google TPU
v4 Pod with 4,096 Tensor Processing Unit (TPU) chips [7],
[16], [17]. Their interconnects differ in system scale, topol-
ogy, and protocol stack. A scale-up protocol configuration
combines choices at the transaction, link-control, physical,
and reliability layers. Transaction semantics define requests,
responses, and operation completion. Link control governs
packet framing, ordering, credits, and retransmission, while
physical-layer choices set lane rate, encoding, propagation de-
lay, and forward error correction (FEC). Reliability, availabil-
ity, and serviceability functions report residual errors and link
degradation [18], [19], [20]. These choices jointly determine
the packet exchanges produced for an operation and the time
required to execute them.

B. Operation-to-Packet Layer
Protocol configurations can impose different dependencies
on the same transfer. For example, a datasendcompletes
when the required bytes reach its destination, while a remote-
memoryloadfirst sends a request and then completes when the
required data return. A common representation must express
various protocols and determine transfer completion from
packet arrivals.
We propose the OTP layer to solve this problem by en-
coding protocol-specific packetization and completion rules
in atransfer-dependency graph. The graph represents one
communication operation, with each transfer contributing a
subgraph. As shown in Algorithm 1, each transfer subgraph
includes four types of nodes: (1) an ACTION node packetizes
and issues a transfer, (2) a W AIT node specifies the data,
response, or acknowledgment required before a data transfer
completes, (3) Optional DELAY nodes insert protocol-defined
delays, and (4) a COMPLETE node marks the end of the
operation. Directed edges define the dependencies between
nodes. At runtime, a node becomes ready after all dependent
nodes have completed, and as illustrated in Figure 2, executing
a transfer subgraph requires the follow steps:
•The initial ACTION node passes packets to PEX when
the operation begins.
•The packets are sent to ns-3 and go through the propa-
gation path.
•The packet arrivals from ns-3 go through PEX and update
the W AIT node.
•The DELAY nodes insert fixed latency to the simulation.
•When COMPLETE becomes ready, OTP records the
current simulation time as the operation completion time.

C. Packet-Execution Layer
The scale-up protocol configuration defines packet-
execution mechanisms, including flow control, switch for-
warding, forward-error-correction (FEC), and retransmission.
Because multiple mechanisms are applied to the same packet,
they jointly affect the packet transfer time. For example, an
error packet will delay credit return, block later injection, and
re-enter the switch queues when retransmitted.
To accurately simulate the packet-execution mechanisms
and their interactions, we propose the PEX layer that composes
the protocol-defined packet mechanisms in one event-driven
execution path. PEX allows each protocol configuration to
select the packet-execution mechanisms and their parameters,
while different protocols reuse the shared PEX implementa-
tion. Figure 5 illustrates a packet’s execution path through the
source device, links, switches, and destination device:
1) Packet execution begins when PEX receives the packets
generated by OTP. The source device will first check
whether the configured flow-control policy permits each
packet to enter the interconnect.

In the PEX path, the protocol-defined packet-execution
mechanisms can mainly be categorized into three groups: (1)
credit-based flow control that governs packet injection, (2)
switched forwarding that selects the outgoing link and arbi-
trates packets waiting for that link, and (3) Link-error handling
that governs FEC and retransmission after a link transfer. We
will introduce how PEX implement these mechanisms in the
following of this part:
Credit-based flow control.The PEX layer supports credit-
based flow control, as used by NVLink, UB, and UALink [21],
[22], [23], [20]. Each virtual channel has a finite number
of credits. Injecting a packet consumes one credit, but when
none remain, the source places the packet in its send queue.
Successful packet delivery sends a credit packet on the reverse
path. The source increments the available-credit count when
this packet returns and then admits queued packets. A delayed
delivery therefore postpones credit return and can block later
injection.
Switched forwarding.At each switch, route selection
chooses the outgoing link. Packets waiting for the same
link share an output queue, and switch arbitration selects
the next packet to send. Packets from concurrent operations
share these output queues and are arbitrated together, so
concurrent operations can delay each another. The PEX layer
also implements packet spraying. When equal-cost paths are
available, packet spraying distributes a transfer across them.
A destination reorder buffer restores packet order before
reporting the transfer’s delivery.
Link-error handling.Our link model combines FEC with
optional link-level retry (LLR), which are widely used by

When the errors exceed the FEC correction capability, PEX
marks the packet as uncorrectable and returns a negative
acknowledgment (NACK) back to the sender. Selective ac-

copy has been evicted, PEX reloads its payload from the
source memory (e.g., HBM) before reinjection. The reload
adds the source-memory access latency according to user’s
configuration and causes the time to re-transmit the packet.
IV. SURROGATE-TO-SIMULATOREVALUATIONFLOW
ProtoBridgeprovides accurate packet-level simulation for
a given superpod design. But emerging superpods introduce
a large and diverse design space across topologies, link tech-
nologies, and protocols, which cannot be efficiently explored
with packet-level simulation alone. For example, the CPO case
study in Section VI-B considers 531 interconnect designs and
72 error-handling configurations, i.e., 38,232 design points.
Exhaustively evaluating these candidates with packet-level
simulation is prohibitively expensive. Therefore, we develop
a surrogate-to-simulator evaluation flow that uses a fast an-
alytical surrogate to explore the design space and applies
ProtoBridgefor accurate validation of promising designs.
A. Protocol-Defined Latency Surrogate
Packet simulation spends most of its runtime on schedul-
ing individual packet events. To enable diverse superpods
evaluation and exploration, we propose a surrogate model
that simplifies the events while keeping the two quantities
exposed byProtoBridge: the transfer parameters defined by
OTP and the latency effects of the mechanisms selected in
PEX. Analytical equations then compute operation latency
directly from the protocol configuration without executing
every packet event. The surrogate divides operation latency
into protocol startup, fixed delay on the critical path of each
transfer, serialized transfer time, and recovery overhead. And
for the transfer time, flow-control stalls, FEC wire overhead,
and contention change the effective throughput of the transfer.

We applyProtoBridgeand the surrogate to two designs

interconnection bandwidth and longer-reach links, motivating
CPO, but optical links add conversion and error-handling
overhead.

B. Case Study II: Full-Optical CPO Fabrics
1) Setup:Electrical link loss rises with signaling rate and
distance, limiting the reach and energy efficiency of high-
speed copper links. Optical transmission has lower reach-
dependent loss, while CPO shortens the electrical path between
the GPU or switch and the optical engine. Prior studies identify
CPO as a promising way to achieve higher bandwidth density
and lower energy per bit [54], [55], [56], [57], [58]. Recent
implementations report 32 channels at 200 Gb/s with twice
the bandwidth density and 30% lower power per bit than an
electrical link [59], [60], [61].
We use optical-electrical (O/E) hybrid interconnection as
the baseline, which selects the link medium by distance.
It uses passive copper for connections up to 2 m, active
electrical cable for connections from 2 m to 5 m, and optical
fiber beyond 5 m [62]. We compare this reach-gated baseline
with full-optical CPO interconnections to determine whether
their higher channel count and data rate improve serving
performance after accounting for optical conversion latency
and link-error handling.
Design space.We use the same LLMs, output length, and
DeepEP modes as Section VI-A. Case Study II evaluates 1,024
GB200 GPUs, each with 186 GB of HBM, 8 TB/s of HBM
bandwidth, and 2.5 peta floating-point operations per second
of dense bfloat16 (BF16) compute [7]. Every input contains
one million tokens, and per-replica batch sizes are from 1 to
1024.
The O/E interconnection has 18 channels at 400 Gb/s and
admits 39 topology configurations. The single-switch NVL-
style fabric from Section VI-A cannot span 1,024 GPUs, so we
exclude it. We add a routed 2D-full-mesh Clos [16], as we are
going to explore CPO with more channels per GPU. CPO uses
32, 64, or 128 channels at 200, 400, or 800 Gb/s, and optical
conversion adds 10 ns at each conversion interface [63], [64].
Combining each channel count with the three rates gives 492
CPO interconnect designs. Together with the 39 O/E designs,
the interconnect space contains 531 points. The pre-FEC BER
ranges from10 −9 to10 −3 [56], [65]. For error handling,
FEC is disabled or uses RS(528,514,7), RS(544,514,15),
or RS(576,514,31)[24], [19]. Retransmission uses GBN
or SACK with a buffer of 0 to 8 MB. We evaluate every
design point at the six BER values, requiring totally 229,392
evaluations.
For each LLM, we form the Pareto frontier of the 18×400-
Gb/s O/E baseline. We choose the point with the largest
product of the TGS and interactivity as the reference for the
following analysis. This choice balances the two metrics rather
than favoring either endpoint.

speedups for the decode operations are 0.99×∼1.40×. The
results show that for prefill communications with large data
sizes, high bandwidth CPO greatly reduces communication
latency. For decode communications, increasing bandwidth
does not bring much benefits as they are latency-dominated;
instead, the conversion latency and error handling overhead of
CPO may increase the communication latency. However, for
decode AlltoAll, increasing channel number provides a 39%
improvement. This is because increasing channel number gives
us a larger topology design space. 64- and 128-channel designs
use 2D-full-mesh topology, compared to leaf-spine topology
in the 32-channel design, the network contention is greatly
reduced for AlltoAll communications.

for three models. Using CPO with 128×800 Gb/s per GPU
reduces TTFT by 0.42%∼7.58%, reduces TPOT by 2.93% for
DeepSeek-V3 and 9.36% for GLM-5.2, but increases TPOT by
2.50% for Qwen3-235B. Although CPO reduces much prefill
communication overhead, the TTFT only decreases slightly as
prefill is compute-bound.

VII. RELATEDWORK
System simulators.Chakra standardizes distributed
machine-learning operations and their dependencies [66].
ASTRA-sim consumes such workloads and models collectives
over analytical or detailed network backends [35], [28], [67].
A recent extension to Chakra also represents collective
algorithms as point-to-point transfers and reductions [68].
SimAI increases training-system fidelity by integrating
framework, kernel, collective, and network models [69],
while Phantora executes unmodified training frameworks and
intercepts their compute and communication operations [70].
LLMServingSim, Vidur, and Frontier instead model serving
schedules, disaggregation, and runtime state [71], [72], [73],
[74]. These systems describe when communication operations
or collective transfers execute.ProtoBridgecontinues from
those operations to protocol packetization, completion
dependencies, and the packet mechanisms selected for a
scale-up design.
Detailed network simulation.ns-3, BookSim, Garnet, and
HTSim resolve packet timing, queues, routing, and switch
behavior [10], [75], [76], [77]. CNSim adds cycle-accurate,
packet-parallel simulation for large chiplet networks, and
Arcadia targets cluster-scale network simulation for artificial-
intelligence workloads [78], [79]. SimBricks composes inde-
pendent simulators [80]. DICE models physical-layer coding,
channel errors, retransmission, and flow control along an inter-
chiplet datapath [81]. These tools execute traffic supplied by a
workload or protocol implementation. Adding a new scale-up
protocol still requires code that generates its traffic and maps
packet outcomes to operation completion.ProtoBridgefactors
those choices into its two-layer configuration.
Analytical performance models.FlexFlow and Proteus
estimate distributed execution while searching parallelization
strategies [8], [9]. Calculon and LLMCompass use parame-
terized analytical models to explore LLM system and hard-
ware designs [82], [83]. Such models make broad exploration
tractable by representing communication with aggregate la-
tency and bandwidth parameters. Our surrogate instead retains
separate terms for the protocol transfer and for delays intro-
duced by flow control, contention, coding, and retransmission.
Section V compares the resulting prediction and design-
ranking accuracy.
VIII. CONCLUSION
In this paper, we proposeProtoBridge, an ns-3-based LLM-
to-packet simulator that enables accurate and efficient evalua-
tion of emerging superpod interconnect designs. ProtoBridge
introduces the OTP and PEX abstraction layers to sepa-
rate protocol-specific packet behaviors from shared packet-
execution mechanisms, allowing diverse scale-up protocols to
be modeled on a common simulation substrate.ProtoBridge
achieves 17.8% and 10.3% average error on H200 NVLink4
and C500 MetaXLink, respectively. To further enable efficient
exploration across large interconnect design spaces, we further
develop a protocol-defined surrogate model that preserves key
protocol effects, enabling a surrogate-to-simulator workflow
that explores thousands of superpod configurations efficiently.
Using this workflow, we analyze emerging superpod designs
with scale-up memory pools and CPO interconnects, providing
architectural insights for future LLM superpod designs.
