# OrbitServe 使用说明

本文介绍不使用本地前端时如何通过命令行运行 OrbitServe，以及相对于 develop 的配置与实验结果变化。

核对日期：2026 年 10 月 30 日。旧版基准为已 fetch 核实的 `origin/develop`，提交 `882688f`；当前版本为 `feature/runtime-dynamic-links` 的 `a9ca323` **加本地未提交改动**。仅获取该分支的已提交版本，并不等于获取了本文核对的完整工作区。

**主实验命令没有更换；卫星实验 JSON 需要迁移，结果读取路径也需要调整。** 当前 CLI 可以独立完成物理预计算、固定设计、DSE 和地面基线，不需要启动网页、服务端或使用指定名称的 Conda 环境。

## 先运行一个完整实验

以下命令均在仓库根目录运行。代码块使用 `python`；Linux 上若解释器名为 `python3`，请统一替换。先激活自己的虚拟环境，再安装当前 checkout：

```text
python --version
python -m pip install -e .
python -m orbitserve.experiments.cli --help
```

包要求 Python 3.11 或以上；本次核验环境是 Python 3.12。核心依赖由 `pyproject.toml` 固定为 NumPy 2.2.6、Astropy 6.1.3、SGP4 2.27 及指定版本的 IERS 数据。让安装命令统一解析依赖，不要单独升级 NumPy。

固定设计：

```text
python -m orbitserve.experiments.cli examples/experiments/fixed_design_geometry.json --out results/mentor/fixed.json
```

DSE：

```text
python -m orbitserve.experiments.cli examples/experiments/orbit_geometry_dse.json --out results/mentor/dse.json
```

地面基线：

```text
python -m orbitserve.experiments.cli examples/experiments/skywalker_ground_reproduction.json --out results/mentor/ground.json
```

单星静态成本计算：

```text
python -m orbitserve.architecture.single_satellite_cost.cli examples/single_satellite/h200_gpu_derived.json --out results/mentor/single_satellite.json
```

这些都是仓库中现有的入口。前两个命令覆盖物理网络到 Runtime 的完整流程；地面基线不运行卫星物理模型；单星成本工具不运行请求仿真。请在完整源码 checkout 中运行示例，当前卫星示例还引用 `tests/fixtures/workloads/coupled_physical`，仅安装 wheel 不会附带这些输入。

### 参数是否变了

| 参数 | develop 与当前版本 |
| --- | --- |
| 第一个位置参数 | 都是实验 manifest 的 JSON 路径 |
| `--out` | 都指定结果 JSON 路径 |
| `--output-mode summary` | 两者都已支持，且都是默认模式 |
| `--output-mode full` 或 `--full` | 两者都已支持，保留完整内存结果的 JSON 表示 |
| `--artifact-dir` | 两者都已支持，用来指定审计产物目录；当前还作为执行产物根目录 |
| `--indent` | 都指定 JSON 缩进 |

因此旧的 `python -m orbitserve.experiments.cli … --out …` 命令形式可以继续用，但它引用的旧 manifest 不保证可用。**summary 加附件并非本轮新引入的模式。**

当前进度写到 stderr。建议始终给出 `--out`；不指定输出路径时，summary 中被精简的大字段可能没有可读取的独立附件引用。即使使用 `--full`，卫星运行也会生成物理数据等文件，不能只保留一个 JSON 就认为所有复现材料齐全。

## 推荐将物理预计算和请求计算分开

一次性试跑用上一节的单命令即可。对同一个星座反复调整 workload、路由、KV 策略、故障或传输后端时，先准备可复用物理数据，可以避免反复运行 SGP4 和链路预算。

### 第一步生成物理数据

```text
python -m orbitserve.experiments.physical_cli compute examples/experiments/fixed_design_geometry.json --out results/mentor/physical --workers 1
```

`compute` 可接收完整实验 manifest，也可接收独立的物理网络 JSON；读取完整 manifest 时只取 `physical_network`，不会计算请求。`--workers 1` 便于首次验证；大实验可按机器资源调高。

默认 `--exports core`，核心物理数据足够 Runtime 使用。完成标志是 `results/mentor/physical/physical_dataset.json`，而不是目录刚创建或已有某个 SQLite 文件。若只需要网络诊断和物理数据，完成这一步即可。

需要展开的帧、位置和 AsterMind 交换数据时，再执行：

```text
python -m orbitserve.experiments.physical_cli export results/mentor/physical --workers 1 --compression-level 1 --chunk-samples 32
```

也可以在 `compute` 时增加 `--exports full`。`--exports full` 属于物理数据导出选项，与主实验的 `--output-mode full` 是两个不同选项。

### 第二步生成引用该数据的实验配置

把下面代码保存为 `results/mentor/prepare_runtime.py`，再从仓库根目录运行 `python results/mentor/prepare_runtime.py`。上一步已经创建了该目录。代码将生成四份运行配置；生成配置不需要安装原生后端。

```python
import copy
import json
from pathlib import Path

source = Path("examples/experiments/fixed_design_geometry.json").resolve()
manifest = json.loads(source.read_text(encoding="utf-8"))
# 新配置放到了不同目录，要重新解析原来相对于示例文件的路径。
manifest["workload"]["bundle_dir"] = str(
    (source.parent / manifest["workload"]["bundle_dir"]).resolve()
)
manifest["physical_dataset"] = str(Path("results/mentor/physical").resolve())
manifest["dse"] = {"enabled": False}

for backend in ("queue", "fluid", "simgrid", "ns3"):
    value = copy.deepcopy(manifest)
    value["experiment_id"] = "mentor_" + backend
    value["physical_network"]["network"]["transport_model"] = backend
    output = Path("results/mentor/runtime_" + backend + ".json")
    output.write_text(json.dumps(value, ensure_ascii=False, indent=2) + "\n",
                      encoding="utf-8")
```

运行不需要额外网络引擎的两种后端：

```text
python -m orbitserve.experiments.cli results/mentor/runtime_queue.json --out results/mentor/queue.json
python -m orbitserve.experiments.cli results/mentor/runtime_fluid.json --out results/mentor/fluid.json
```

这两次运行应显示 `Loading complete physical dataset (no physical recomputation)`。每个实验仍有自己的请求、队列、KV 和故障状态。输出目录使用不同名称，避免与旧配置的物理缓存混用。

配置也可只保留 `physical_dataset` 而省略 `physical_network`，此时使用数据集内保存的物理输入。上面的脚本保留两者，是为了显式覆盖传输后端。

### 哪些修改需要重新预计算

| 修改内容 | 是否可复用同一份物理数据 |
| --- | --- |
| workload、Serving 配置、Runtime 权重、路由、KV 复制开关 | 可以，但仍需满足模型名称、编队规模等一致性约束 |
| `network.transport_model` | 可以 |
| `network.faults`、`random_faults`、`fault_timing`、恢复策略和重试次数 | 可以；这些是 Runtime 输入 |
| 独立 `route_probes` | 不改变物理身份；仅运行 Runtime 不会重新执行物理阶段的 probes |
| 星座、TLE、时间范围、`step_s`、地面站位置或终端数 | 需要重新计算 |
| 拓扑、终端分配或切换策略、链路预算、容量模型、太阳规避角 | 需要重新计算 |

当前物理数据 schema 是 `orbitserve.physical_dataset.v2`，物理版本为 `sample_hold_directional_solar_visibility_islsim_v4`。加载时检查模型语义、输入身份和文件 SHA-256。不要手动编辑数据集文件；显式引用缺失、损坏、版本过期或不匹配的数据集会报错，不会自动重算。历史结果可以作为历史记录保留；不等于旧物理数据可以用于当前新仿真。

## 配置文件从 develop 到当前有哪些变化

### 顶层结构和字段迁移

| 旧输入或旧示例写法 | 当前写法与迁移动作 |
| --- | --- |
| `constellation.orbital_sets` 或 `constellation.shells` | 改为 `physical_network.constellations.communication_shells` 和 `compute_formations`，分别描述通信卫星和计算编队 |
| `simulation.epoch`、`duration_s`、`step_s` | 改为 `physical_network.time.epoch_utc`、`duration_s`、`step_s` |
| `simulation.trace_model` 和旧 `trace_options` | 无一一对应的整体搬运方式；当前生产计算走逐星 SGP4 和物理网络输入 |
| `constellation.gateway_profile` | 地面节点放入 `physical_network.ground_ingresses`，链路预算放入 `physical_network.network.link_profiles.sgl`，终端限制在相应节点或星座配置中声明 |
| `hardware.mode: from_cost_case`、`source_case_path` | 当前使用显式 `HardwareSpec`，例如 `accelerator`、`compute_payload`、`communication`、`power`；不能继续只引用旧 cost case |
| 单一硬件配置 | `hardware` 描述计算卫星；新增可选 `communication_hardware` 描述通信卫星。省略后者时会复用计算卫星硬件，可能明显高估通信星成本 |
| 旧示例中的 `scheduler` | 卫星实验使用 `runtime_strategy`；地面实验使用 `ground_baseline`。基准 develop 的加载器也已经拒绝 `scheduler`，这是旧示例与代码脱节，不能当成旧接口仍受支持 |
| `workload.bundle_dir` | 保留，仍指向 canonical bundle |
| `serving`、`runtime_strategy`、`costing` | 概念保留，但必须符合当前字段校验，不能搬入旧 scheduler 的任意字段 |
| 新增 `physical_dataset` | 可选，用于直接复用已完成物理数据；单命令模式不要求填写 |
| DSE 的短名称扫描键，例如 `planes` | 改为物理网络对象内的完整字段路径，例如 `constellations.communication_shells.0.source.planes` |

旧卫星 JSON 若仍含 `constellation` 或 `simulation`，当前加载器会以 `Unsupported experiment fields` 拒绝。文件中写着同一个 schema 字符串也不代表字段兼容；以当前加载器和示例为准。

当前卫星实验的结构如下。这里是字段说明，不是可以单独运行的完整 JSON；完整参数请从 `examples/experiments/fixed_design_geometry.json` 复制。

```text
experiment_id
physical_network
  time
  constellations
    communication_shells[]     通信壳层的 Walker 或 TLE 输入
    compute_formations[]       每个计算编队的来源、成员和内部拓扑
  ground_ingresses[]           地面入口及终端约束
  network
    link_profiles              通信 ISL、编队 ISL、跨层链路、星地链路
    transport_model            queue / fluid / simgrid / ns3
    ground_access_policy       物理接入偏好
    handover_policy            动态接触保留或重新排序
    faults / random_faults     Runtime 故障输入
  route_probes[]               独立网络探针，可为空
hardware                       每颗计算卫星的硬件
communication_hardware         每颗通信卫星的硬件，可选
serving                        模型、并行度和计算编队通信近似
workload.bundle_dir            请求输入
runtime_strategy               调度权重、路由和 KV 策略
physical_dataset               已完成数据集，可选
dse                            设计扫描，可选
costing                        成本口径，可选
```

### 修改参数时要同时满足的约束

- `serving.formation.member_count` 必须等于每个物理计算 cell 的成员数。当前固定设计示例是每 cell 4 颗计算卫星，并非全星座只有 4 颗星。
- workload 中的 `model_family` 必须与 `serving.model.name` 一致。只改 Serving 的模型名称可能直接报错。
- `runtime_strategy` 的 `latency_weight`、`kv_reuse_weight`、`energy_weight`、`compute_load_weight` 均非负且总和为 1。
- `routing_policy` 支持 `min_hops`、`min_propagation`、`earliest_arrival`，默认后者。物理 `ground_access_policy` 和 Runtime 路由是不同参数。
- 节点 ISL 终端数及链路配置带宽不能超过 Architecture 硬件能力；`bandwidth_bps` 单位为 bit/s，硬件里的 `*_gbps` 为十进制 Gbit/s。
- workload 的 `ingress_id` 必须能在物理地面入口中解析；新时间范围应覆盖 workload 的请求释放与执行需求。
- 将 manifest 移到其他目录后，必须重新检查 `workload.bundle_dir`、`physical_dataset`、外置 `physical_network` 和 TLE 路径。相对路径以声明它的配置文件所在目录为基准；CLI 的 `--out` 相对当前工作目录。

不要把前端保存的整个 scene 包装 JSON 直接交给共享 CLI。共享入口需要的是 `ExperimentSpec` 对象对应的 manifest；本地 scene 中还可能有 `experiment` 包装、素材引用或 `local_*_workload` 标志，需要先解析成真实物理输入、实际 bundle 路径和共享字段。复制网页上的参数时，以完整实验 manifest 为交付物。

### workload 文件到底变没变

**相对于本次核对的 develop，canonical workload 没有从七文件迁到六文件。加载器在两边都使用下面六个文件；旧 README 的七文件说明有误。**

```text
workload_manifest.json
regions.json
gateways.json
session_requests.jsonl
timebin_demand.csv
workload_summary.json
```

已有合法六文件 bundle 可继续使用，无须为本轮改动拆成 `requests.jsonl` 和 `sessions.jsonl`。若手头确实只有这两个旧文件，不能只改名，应通过对应 workload adapter 转成当前 canonical bundle，并校验摘要中的哈希。

`orbitserve.workload.causal.v1` 在基准 develop 中也已存在。后续轮次依赖上一轮完成再加 `inter_turn_gap_s` 的语义，不是本轮刚增加。不要为了适配新网络模型而把因果请求强行改成绝对时间请求。

可独立检查已有 bundle：

```text
python -c "from orbitserve.workload import load_workload_bundle; b = load_workload_bundle('tests/fixtures/workloads/coupled_physical'); print(b.summary)"
```

主示例的 workload 路径确实换成了小型 `coupled_physical` fixture。**格式未变，不等于这次示例仍使用原来的实验数据。**

## 传输后端和外部模型怎样选择

### Runtime 的四种后端

在 `physical_network.network.transport_model` 中设置：

| 后端 | 计算方式 | 额外依赖 |
| --- | --- | --- |
| `queue` | 默认；逐跳整消息占用链路方向及相应 RF 共享资源，后来的消息排队 | 无原生网络库 |
| `fluid` | 逐跳流体共享；活动传输、完成和容量事件更新服务速率 | 无原生网络库 |
| `simgrid` | 原生 SimGrid 4.1 CM02 共享链路传输 | 安装 `.[simgrid]` 及平台构建依赖 |
| `ns3` | 原生 ns-3 分包传输；模型中有包边界、填充及 PPP 开销 | 安装 `.[ns3]` 并提供 C++20 编译器 |

先用 queue 跑通。要比较并发带宽分享，再运行前面生成的 fluid 配置。SimGrid 和 ns-3 使用真实原生依赖，缺失时直接报错，没有自动降级。

原生依赖安装方法见 [README 的 Physical Network Model 节](../README.md#physical-network-model)，特别是 SimGrid 的 `tests/requirements/native-build.txt` 构建约束。具备对应环境后执行：

```text
python -m orbitserve.experiments.cli results/mentor/runtime_simgrid.json --out results/mentor/simgrid.json
python -m orbitserve.experiments.cli results/mentor/runtime_ns3.json --out results/mentor/ns3.json
```

四种后端共用几何、链路预算和 workload，不保证延迟相同。ns-3 适配层负责这里的逐跳串行化与竞争，OrbitServe 仍负责路由、传播与故障恢复；不能把它解释成完整 TCP/IP 协议栈实验。

### ISLSim 与 Serving 外部测量

ISLSim 是计算星间光链路物理速率的外部模型，和上面四种传输后端是两个独立选择。

- 新 JSON 星间光链路 profile 若省略 `capacity_model`，当前会按 `islsim` 处理；通信 ISL、cell ISL 和跨层光链路都要留意。
- 仓库当前两个卫星示例显式使用 `fixed` 光链路容量，所以可以不依赖 ISLSim checkout；星地示例使用 RF Shannon 预算。
- 要实际使用 `islsim`，将 `ORBITSERVE_ISLSIM_ROOT` 指向已授权取得的 ISLSim checkout，并在 profile 内提供所需 `islsim_config`。当前源码适配器也支持回退读取 `local/config/communication-modules.json`，但 mentor 的机器未必有此个人文件，交付时应使用显式配置。`ORBITSERVE_ISLSIM_CONFIG` 可供本地 `resolve_islsim_config()` 辅助函数选择原生 JSON，不会自动改写已冻结 profile 的参数。
- 只生成原生配置文件可以独立执行下面的命令，不会加载 ISLSim 实现：

```text
python -m orbitserve.experiments.islsim_cli --out results/mentor/islsim.json
```

可选 `--input profile.json` 接收原生 `tx`、`rx`、`channel` 或 profile 的 `islsim_config`。换容量模型或预算参数后，需要新建物理数据集。

Serving 默认仍使用解析性能模型。`serving.external_profile` 可以导入 AsterMind 的 `orbitserve.astermind_measurements.v1` 测量表，但共享 CLI 不会自动构建或运行 AsterMind。测量必须匹配模型、硬件、编队和并行度，并覆盖 prefill/decode 及配置的并发度；单个总时延数字不构成可用速率表。

## 实验输出怎样读取

### 文件在哪里

对固定设计命令 `--out results/mentor/fixed.json`，当前主要产物为：

```text
results/mentor/
  fixed.json                           summary 和附件引用
  fixed_artifacts/
    experiment_result.json             完整实验结果
    runtime_events.jsonl.gz            Runtime 事件
    runtime_requests.jsonl.gz          嵌套结构的逐请求结果
    runtime/
      request_records.jsonl            summary 外置的逐请求结果
      decision_trace_records.jsonl     决策记录，存在记录时生成
      events.jsonl                     summary 外置的 Runtime 事件
    network/
      physical_dataset.json            此次使用的物理数据身份和哈希
      materialized_input.json          冻结的物理输入
      core_result.json                 核心网络索引
      network_result.json              网络结果视图
      physical_state.sqlite            物理链路属性
      orbit_trace/                     轨道数据
      state/                           位置和时间线索引
```

文件引用以实际 `artifact_manifest` 和 `network.result_index` 为准。地面基线没有这整套卫星网络产物。DSE 另外生成候选目录和 `dse/rows_full.jsonl`；候选的完整 Runtime 数据读该附件。

`frames/`、`node_positions.jsonl.gz`、`link_attributes.jsonl.gz`、`link_events.jsonl.gz`、`astermind_network.jsonl.gz` 等展开视图属于可选物理导出；core 模式下没有它们不表示计算失败。用前述 `physical_cli export` 从对应数据集补导出。

### 原有绘图和统计脚本改哪些字段

下表针对**卫星实验**：

| 信息 | develop 结果 | 当前结果 |
| --- | --- | --- |
| 硬件与架构 | `constellation_architecture` | `architecture.compute`、`architecture.communication` |
| Serving 明细 | 主要在 `performance` 及其 details 中 | 顶层 `serving` |
| Runtime 汇总 | `performance.details.runtime` | 顶层 `runtime` |
| 请求总数与完成数 | `performance.details.runtime.request_summary` | `runtime.request_summary` |
| TTFT、TPOT、E2E 分布 | `performance.details.runtime.inference_metrics` | `runtime.inference_metrics` |
| 逐请求结果 | 旧 Runtime 的 `request_records` 或其附件 | `runtime.request_records_path` 引用的文件，或 full 中的 `runtime.request_records` |
| 总成本 | `cost.total_cost_usd` | 仍是 `cost.total_cost_usd`，新增计算与通信两类分解 |
| 顶层 SLO 对象 | `slo` | 当前不再输出该顶层对象；不能继续读 `result['slo']` |
| DSE 前沿 | `dse.frontier` 等旧对象 | `dse.rows`、`dse.selected_rows`，每行含完成比例、成本、E2E p95 和选择标志 |

例如读取固定设计汇总：

```text
python -c "import json; from pathlib import Path; r=json.loads(Path('results/mentor/fixed.json').read_text(encoding='utf-8')); print(r['runtime']['request_summary']); print(r['runtime']['inference_metrics']); print(r['cost']['total_cost_usd'])"
```

当前卫星逐请求 JSON 是分区结构：

```python
# row 是 runtime/request_records.jsonl 的一行。
request_id = row["request"]["request_id"]
completed = row["outcome"]["completed"]
ttft_s = row["timing"]["ttft_s"]
e2e_s = row["timing"]["e2e_s"]
path = row["routing"]["selected_path"]
```

TTFT、TPOT、E2E 的 `average/p50/p95/p99` 统计只包含完成请求；失败请求的延迟为 null。看延迟时必须同时报告 `completed_request_count / total_request_count`，否则大量失败的方案可能看起来反而更快。TPOT 继续按 `(E2E - TTFT) / (output_tokens - 1)` 计算，输出不足两 token 时为空。

当前卫星结果没有现成的总体 SLO 达标率对象。若要统计达标率，应按 `request_id` 将逐请求结果与 bundle 中的 `ttft_deadline_s`、`e2e_deadline_s` 关联，明确分母和失败请求处理，再计算完成且满足 deadline 的比例。不要把“完成比例”标成“SLO 达标比例”。

**地面基线的结果契约不同**：聚合指标读取 `runtime.runtime_metrics`，逐请求仍是平铺的地面 record；不应套用上述卫星分区字段。地面成本在 `cost`，只有实际配置了 terrestrial costing 并且结果标明 evaluated 时才能用于成本比较。

## 实验结果为什么可能与以前不同

### 默认示例已经换了场景

| 项目 | develop 同名固定设计示例 | 当前同名固定设计示例 |
| --- | --- | --- |
| 轨道输入 | `constellation.orbital_sets`，配置圆轨道近似 trace | 独立通信壳层和计算编队，逐星 SGP4 |
| epoch | 2026-06-16 | 2026-07-20 |
| 时长与采样 | 600 秒，60 秒采样 | 120 秒，1 秒采样 |
| 星座配置 | 2 轨道面 × 2 cell × 每 cell 2 星 | 24 颗通信星 + 2 cell × 每 cell 4 颗计算星 |
| 地面入口 | 原 workload 网关和 direct request 输入 | 显式 `ground-00` |
| workload | `trace_replay_three_region_public_shape` | `coupled_physical`，3 个请求 |

这两份同名示例不是同一输入，不能用它们的时延或总成本计算“本轮提高了多少百分比”。旧示例还存在 `scheduler` 等与当时加载器不一致的字段，直接拿它执行失败也不能算成旧模型的性能数据。

当前 `orbit_geometry_dse.json` 扫描 Grid/Honeycomb 两种通信拓扑和 750/800 km 两种计算高度，共 4 个物理设计；旧同名示例扫描轨道面数和每面 cell 数，候选集合已改变。当前 `skywalker_ground_reproduction.json` 也改为单区域、两副本、3 请求的合成 smoke 输入；文件名保留不代表它仍执行原来的多区域论文方法复现实验。

### 模型变化会改变什么

| 变化 | 可能反映到的结果 |
| --- | --- |
| 通信星与计算星拆分，计算 cell 有真实成员和内部连接约束 | 路径、可达性、部署可行性和两类卫星成本 |
| 动态终端分配、捕获时间、链路窗口及切换策略 | 请求等待、路由和失败原因 |
| 距离与环境相关的 RF/光链路预算、方向速率及 RF 共享池 | 上下行速率、拥塞和返回时延 |
| 按时间排序的请求、逐跳传输、计算和返回事件 | 到达顺序、队列竞争、KV 可见性和实际完成时间 |
| queue、fluid、SimGrid、ns-3 的不同服务模型 | 并发时延、包开销和容量变化响应 |
| 可选故障与恢复 | 完成比例、丢弃的在途字节、恢复路径和恢复耗时 |
| 逐节点及链路端点的能量检查 | SOC、通信能耗和能量导致的不可调度 |

这些变化不具有统一的“结果更大”或“结果更小”方向。当前生产位置、日照和环境链路属性按最近物理采样保持；请求到达、计算和传输仍以实际事件时间执行，`step_s=1` 不表示请求延迟会被取整到秒。容量计划边界也独立生效。

故障实验务必显式设置 `network.fault_timing`：当前代码默认 `continuous`，也支持 `boundary`。`failure_policy` 默认 `fail`，选择 `retry_next_sample` 才启用对应的恢复尝试；计算节点故障不提供模型 checkpoint 恢复。旧说明中出现过 boundary 默认值的描述，以本次代码和 manifest 的显式配置为准。

### 正式比较时固定哪些条件

1. 为每次实验记录代码提交及未提交补丁、完整 manifest、bundle 哈希、物理输入/数据集哈希、依赖版本和随机种子。
2. 比较 Runtime 策略或后端时，使用同一份完成的物理数据、同一 workload、同一 Serving 和成本参数；每种配置使用独立输出目录。
3. 比较旧模型与新物理模型时，先对齐 epoch、时长、物理卫星数、每星硬件、编队、入口、请求和统计口径；保留无法一一映射的模型假设。
4. 同时报完成比例、TTFT/TPOT/E2E 分布、失败原因、成本以及需要研究的 KV/能耗指标。需要 SLO 结论时另算 deadline 达标率。

当前 DSE 的 `selected` 依据完成比例、总成本、E2E p95 的非支配关系，不等价于按 workload deadline 判定的 SLO 前沿；没有 E2E p95 的候选不会被选入。旧静态 SLO proxy、旧 frontier 字段或自定义 objective 不能直接沿用；部分旧 runtime-matrix 控制项会被明确拒绝。

## 常见问题与处理

| 现象 | 处理 |
| --- | --- |
| `No module named orbitserve` | 在当前解释器和 checkout 中运行 `python -m pip install -e .`，检查是否误用了另一个环境 |
| `Unsupported experiment fields` | 移除旧顶层字段，按当前示例重建 manifest；不要只改文件名 |
| `Unsupported HardwareSpec fields` | 使用显式硬件字段，迁移 `mode/source_case_path` 等旧示例写法 |
| 找不到 workload 或摘要校验失败 | 检查 manifest 相对路径、六文件完整性和摘要哈希 |
| `model_family must match` | 对齐 workload 模型与 Serving 模型 |
| `formation.member_count` 不匹配或终端能力超限 | 同时修改物理 cell、Serving 编队和硬件能力 |
| 物理数据未就绪、损坏、语义过期或身份不符 | 新建输出目录，重新执行 `physical_cli compute`，不要修改哈希绕过检查 |
| 输出目录已有不同的缓存网络输入 | 换一个实验输出路径；`--out` 名称决定默认产物目录 |
| 找不到 ISLSim | 显式选择有意采用的容量模型，或配置可用 ISLSim checkout；重新准备对应物理数据 |
| 原生 SimGrid/ns-3 不可用 | 安装匹配依赖及编译工具，或显式改用 queue/fluid；改后端不需要重算物理数据 |
| 找不到旧 `performance`、`slo`、`frontier` 字段 | 按本文结果路径迁移统计脚本 |
| 网络文件生成了，但有请求未完成 | 先看 `runtime.request_summary.uncompleted_reason_breakdown`，再关联请求记录和事件日志；CLI 成功退出不表示请求全部成功 |
